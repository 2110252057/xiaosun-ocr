# 小孙OCR

本地离线 OCR 工具。识别全部在本机完成，**无需联网**。

支持**三种截屏识别**（无障碍 / root / 录屏授权，自动挑选）、图片文件识别、
**摄像头实时识别（只认数字）与相册图片识别（显示原图 + 框出数字行）**，
提供本地 HTTP 接口与 **MacroDroid / Tasker 插件**能力，
并内置**边缘滑动手势触发器**（含跟手滑出菜单），支持**从最近任务隐藏**，方便接入自动化流程。

## 一、技术构成

| 层 | 说明 |
|---|---|
| 推理引擎 | 自编译 native 库（2 个 ABI），基于 PP-OCRv6 模型；`rapid` 档改由 ML Kit 承担 |
| 模型档位 | `tiny`（轻量，native）/ `small`（高精度，native）/ `rapid`（ML Kit 捆绑版，英文+中文） |
| JNI 绑定 | 静态符号绑定，类名与方法签名须与 native 库一致 |
| 服务与接口 | 前台服务 + 本地 HTTP（127.0.0.1:1666） |
| 插件 | 完整实现 Tasker/Locale 协议，支持异步变量回传 |
| 截屏 | 无障碍截图（API 30+，免 root 免授权）/ root `screencap` / MediaProjection，自动挑选 |
| 摄像头 | Camera2 后置实时识别，YUV 帧转位图送本地引擎，结果只保留数字 |
| 边缘手势 | 悬浮窗手柄 + 8 方向判定，可跟手滑出菜单，结果经插件事件通道回传 |
| 界面 | 程序化 UI，两个页签（OCR设置 / 滑动触发） |

> **JNI 约定**：native 库没有 `JNI_OnLoad`，无法动态注册，
> 符号形如 `Java_<包名下划线化>_<类名>_<方法名>`，当前为
> `Java_com_xiaosun_ocr_OCRService_*`。
> ⚠️ 改动包名 / 类名 / 方法签名必须同步重编 native 库，否则启动即 `UnsatisfiedLinkError`。

## 三、MacroDroid 插件

本 App 是一个 **Tasker/Locale 兼容插件**，MacroDroid / Tasker 可直接调用。

> 📖 **开发细节另见**：[MACRODROID_PLUGIN_GUIDE.md](MACRODROID_PLUGIN_GUIDE.md)
> —— MacroDroid 没有官方插件文档，那份指南是反编译 MacroDroid + PP-OCRv6 插件
> 得到的完整协议说明（常量表、能力位、异步回传机制、踩坑记录）。

### 配置步骤

1. 新建宏 → 动作 → **Tasker/Locale Plugin**
2. 在插件列表里选 **小孙OCR**
3. 在配置界面设置：
   - **图片来源**：截取当前屏幕 / 指定图片路径
   - **模型档位**：tiny / small / rapid
   - **输出格式**：纯文本 / 含坐标
   - **指定文本**（可选）：要查找的文字
   - **匹配方式**：包含文本 / 匹配文本（完全一致）
4. **保存**（保存时才会把变量清单告知宿主）
5. 在动作里展开 **Output variables**，把需要的变量映射到宏变量

### 回传的变量

| 变量 | 类型 | 内容 |
|---|---|---|
| `%xsocr_text` | 文本 | 识别出的全部文本（多行用换行或空格拼接） |
| `%xsocr_match` | 文本 | 指定文本是否找到：`true` / `false` |
| `%xsocr_x` | 文本（数字） | 命中处的 x 坐标；未找到为 `-1` |
| `%xsocr_y` | 文本（数字） | 命中处的 y 坐标；未找到为 `-1` |
| `%xsocr_error` | 文本 | 出错信息（失败时才有内容） |
| `%xsocr_time` | 文本 | 耗时（毫秒） |
| `%xsocr_tier` | 文本 | 实际使用的档位 |

> 坐标基于**截图原始像素**，可直接用于点击坐标。

**触发器（事件）路径**回传的是另一组变量 —— 手势本身不发识别请求：

| 变量 | 类型 | 内容 |
|---|---|---|
| `%xsocr_menu_index` | 文本（数字） | 滑动菜单选中项序号（从 0 开始）；**没选中就不传这个变量** |
| `%xsocr_menu_text` | 文本 | 选中项的名字；没选中就不传 |
| `%xsocr_menu_action` | 文本 | 选中项的动作值；没选中就不传 |

> 手势方向**不单独回传**：插件在收到查询时就已经在内部做过方向匹配，
> 不匹配的这次直接回 17、宏根本不跑 —— 能跑起来的宏就是方向对的那个。
> 详见 [MACRODROID_PLUGIN_GUIDE.md](MACRODROID_PLUGIN_GUIDE.md) 第 7.4 / 7.6 节。

### 匹配方式说明

| 方式 | 行为 | 例子（查找「确定」） |
|---|---|---|
| **包含文本** | 文本块含这几个字即算命中 | 匹配「确定提交」「请点确定」 |
| **匹配文本** | 整个文本块与它完全一致 | 只匹配「确定」 |

两者均**不区分大小写**，取第一个命中的文本块。

### 实现说明

- **异步变量回传**：宿主发有序广播后只等 11 秒，超时即丢弃结果。
  本插件先回 `RESULT_CODE_PENDING`，再通过宿主预置的 `COMPLETION_INTENT`
  在识别完成后补送变量，因此**不受该超时限制**。
- **服务自动拉起**：插件触发时若 App 已被回收，会在广播豁免窗口内
  `startForegroundService()` 重新拉起服务。
- **截屏授权自动申请**：无 root 时截屏需要 MediaProjection 授权，
  而该授权只能由 Activity 发起。插件会拉起透明的
  `ScreenCaptureRequestActivity` 代为申请（需「悬浮窗权限」）。
- **无障碍截图免去授权**：若用户开启过「无障碍截图」（见第五节），
  截屏走这条路径，插件**既不需要悬浮窗权限、也不会弹授权框** ——
  这是无人值守场景最省事的一种配置。
- 协议常量**手写内联**，不引入已归档的第三方库（`PluginContract.java`）
- 识别统一走本地 HTTP（1666），与 App 内、外部脚本**完全同一条路径**

#### 为 Tasker 兼容性修过的两处

变量一直能正常回到 MacroDroid，但在 Tasker 里收不到。排查后是两个独立的原因，
都属于「按 Tasker 官方 `TaskerPlugin.java` 的对齐」，且**都只影响 Tasker、
不影响 MacroDroid** —— 所以此前一直没暴露：

**① 结果走「服务」还是「广播」，读错了 Intent。**

Tasker 回传结果有两种通道：把结果 `startService()` 给宿主的服务，或直接
`sendBroadcast()`。走哪条由宿主预置在 `COMPLETION_INTENT` 里的三个值决定
（`EXTRA_CALL_SERVICE_PACKAGE` / `EXTRA_CALL_SERVICE` / `EXTRA_CALL_SERVICE_FOREGROUND`）。
官方是从**解析后的 completion intent** 上读这三个值；我们原先从**触发时的原始
intent**（`fromHost`）上读 —— 那上面根本没有这三项，于是恒为 null，
一律走了 `sendBroadcast`。MacroDroid 收广播，正常；**Tasker 是按服务收结果的，
广播到不了它手里，变量就全丢了。** 现在改从 completion intent 读，
读不到再回退 `fromHost`（只加不减）。

**② 变量的值类型必须是字符串。**

官方 `addVariableBundle` 的 javadoc 写得很死：

```
* Names must be valid Tasker local variable names.
* Values must be String, String [] or ArrayList<String>
```

即**只接受 String / String[] / ArrayList&lt;String&gt;**。而我们曾经「为了更规范」
用 `putInt()` 回传菜单索引与命中坐标 —— Tasker 收到 Integer 会**静默丢掉该项**
（同批 `putString` 的照收），现象正好是「**文字变量能到、索引和坐标到不了**」。
MacroDroid 内部对每个值统一 `toString()`、不挑类型，所以这个坑只在 Tasker 一侧出现。

现在一律用 `PluginContract.putIntAsString()` 写成字符串（`"3"` / `"-1"`），
宏侧拿到的文本与之前完全一致，语义零变化。

### ⚠️ 两种「免授权」配置，任选一种

MacroDroid 在后台触发插件时，App 可能处于后台或已被回收。
默认情况下要让插件能**自动弹出截屏授权框**，需要 `SYSTEM_ALERT_WINDOW`
（悬浮窗）权限 —— Android 10+ 只允许拥有该权限的应用从后台启动 Activity。

开启方式：App 内「OCR设置」页 → 屏幕截屏识别卡片 → **悬浮窗权限** 按钮。

> 不开也能用，但需要先手动打开一次 App 完成截屏授权；
> 授权在服务存活期间有效，服务重启后需要重新授权。

**但如果你用了下面任一种方式，连悬浮窗权限都不需要：**

| 方式 | 条件 | 效果 |
|---|---|---|
| **无障碍截图** | Android 11+，勾选一次 | 免 root、免授权、不弹框 |
| **root 截屏** | 设备有 root | 免授权、不弹框 |

两者都会让 `screenCaptureReady` 直接为 `true`，插件跳过整个授权流程。
详见第五节。

## 四、接口协议

- 地址：`http://127.0.0.1:1666`

### 路由

| 路由 | 说明 |
|---|---|
| `POST /` | 识别（`path` 可选，不传则自动截屏） |
| `GET /last` | 读取上一次识别结果（JSON） |
| `GET /last?format=text` | 同上，返回纯文本 |
| `GET /ocr?format=text` | 一步完成「取图 → 识别 → 返回文本」 |

### POST / 参数

支持 JSON Body / form 表单 / query 三种方式：

| 字段 | 说明 |
|---|---|
| `path` | 图片绝对路径（需文件权限） |
| `type` | `1`=纯文本　`2`=Json数组(含坐标)　`3`=详细Json(含矩形) |
| `tier` | 可选：`tiny`（轻量，默认）/ `small`（高精度）/ `rapid`（ML Kit，英文+中文）。切换后**持续生效** |
| `action` | 可选：`setTier` 表示只切档位、不做识别 |

> **不传 `path` 时自动截屏识别**（有 root 走 `screencap`，无需授权）。
>
> **模型档位**是全局状态，切一次对所有后续请求生效——外部调用与 App 内切换共用同一状态。
>
> 三档差异：
> | 档位 | 特点 |
> |---|---|
> | `tiny` | 最快，模型最小，字典 6904 |
> | `small` | 字典 18708，保留更多标点/符号 |
> | `rapid` | **ML Kit 文字识别（捆绑版）**：模型随 APK 打包，**不需要 Google Play 服务、不联网下载**；英文 + 中文（中英混排），输出行级包围盒与置信度 |
>
> ⚠️ **不支持 `base64` 传图。** 原因：base64 会让请求体膨胀 33%，
> 且服务端要先整块解码成字节数组再解码位图，一张 4K 图峰值内存可达 60MB+，
> 低端机容易 OOM。改用 `path` 后由 `decodeFileSafe` 直接按需降采样，内存可控。

- **状态码（修复⑨）**：HTTP 状态码与响应体里的 `status` **保持一致**。
  例如图片不存在 → HTTP `404` **且** body `{"status":404,...}`；
  模型尚在加载 → HTTP `503` **且** body `{"status":503,...}`。
  于是 `curl -f`、Auto.js、OkHttp 等只看状态码的调用方也能正确判错。
  > ⚠️ 唯一例外：`GET /last` **恒回 HTTP 200** —— 它是"探活"接口，
  > 只要服务在监听就算通；"还没有识别记录"属于业务状态，写在 body 的 `status` 里。
  > 插件路径（`PluginFireReceiver`）读的始终是 body 内的 `status`，不受影响。

- 响应：JSON 文本，成功 `{"status":200,...}`，失败 `{"status":400/404/500/503,"data":"Error: ..."}`

### 调用示例

```bash
# 启动后台服务（供自动化脚本使用）
am start-foreground-service com.xiaosun.ocr/.OCRService

# 传路径识别
curl -X POST http://127.0.0.1:1666 -H "Content-Type: application/json" \
     -d '{"path":"/sdcard/test.png","type":1}'

# 不传 path：自动截屏识别
curl -X POST http://127.0.0.1:1666 -H "Content-Type: application/json" \
     -d '{"type":3}'

# 只切换模型档位（不识别）
curl -X POST http://127.0.0.1:1666 -H "Content-Type: application/json" \
     -d '{"tier":"small","action":"setTier"}'

# 识别的同时切换档位
curl -X POST http://127.0.0.1:1666 -H "Content-Type: application/json" \
     -d '{"path":"/sdcard/test.png","type":1,"tier":"small"}'

# 一步完成截屏+识别，直接拿纯文本
curl "http://127.0.0.1:1666/ocr?format=text"

# 读取上一次识别结果
curl "http://127.0.0.1:1666/last?format=text"
```

```javascript

        { "path": "/sdcard/test.png", "type": "1" });
log(res.body.string());
```

## 五、截屏识别：三种方式自动挑选

不传 `path` 时，服务会自行截屏。截屏有**三条**路径，**按顺序自动挑选**，
前一条失败就往下试，不会因为某条路临时失效就整体不可用：

| 优先级 | 方式 | 是否需要授权 | 说明 |
|---|---|---|---|
| ① | **无障碍截图** | **勾选一次，永久免授权** | `AccessibilityService.takeScreenshot()`，需 Android 11+、不需要 root |
| ② | **root 截屏**（`screencap`） | **完全不需要** | `su -c screencap -p <path>`，App 启动时自动探测 |
| ③ | **MediaProjection** | 每次重启都要点一次「开启截屏授权」 | 前两者都不可用时的兜底 |

### ① 无障碍截图（最省事）

Android 11（API 30）给无障碍服务开了 `takeScreenshot()`。用户只需在系统
「设置 → 无障碍」里**勾选一次**，之后本应用随时可截、不弹框、不需要 root。

开启方式：App 内「OCR设置」页 → 截屏识别卡片 → **无障碍截图** 按钮，
在列表里找到「**小孙OCR 截图**」并开启。

> **它是可选的一条路，不是必需。** 不开也不影响其它功能，只是退回 ② / ③。

**关于隐私**：该服务 `onAccessibilityEvent` 是**空实现**，配置里也
**没有声明任何 `accessibilityEventTypes`** —— 它收不到屏幕文本、控件树、
点击或按键事件，只保留「截图」这一项能力。用户勾选它，等于只说了一句
「允许你在需要时截一张屏」。

> 实现要点：`takeScreenshot()` 是回调式 API，而 `captureScreen()` 是同步
> 返回 `Bitmap` 的老接口，中间用 `CountDownLatch` 桥接（8 秒上限）。
> 回调给的 `HardwareBuffer` 包装出的是 HARDWARE 位图，必须在
> **关闭缓冲之前** `copy(ARGB_8888)` 落到软件内存，否则 OCR 引擎读不到像素。

### 行为说明

- **开了无障碍**：任何设备（Android 11+）都直接可用，**不需要 root、
  不需要录屏授权**。这是无人值守最推荐的一种配置。
- **有 root 的设备**：服务启动后自动启用 root 截屏（会先试拍一张确认可用），
  `screenCaptureReady` 直接为 `true`，调用方**无需任何授权步骤**，
  也不会出现系统录屏确认框。适合无人值守 / 自动化脚本场景。
- **两者都没有的设备**：需在 App 内点一次「开启截屏授权」，
  且服务重启后需要重新授权。
- 界面「屏幕截屏识别」卡片会显示当前走的哪条路径，
  并提供 **无障碍截图** / **检测 root 截屏** / **开启截屏授权** 三个入口。
- 任一条路在某次调用中失败（例如 SELinux 临时拦截、投屏会话失效），
  会自动**回退到下一条**，不会直接报错。

### 为什么用 `screencap`

`screencap` 是 Android 自带的系统命令，root 下可直接抓取当前屏幕，
只依赖一次 `su` 授权（由 Magisk / SuperSU 管理，一次授权长期有效），
与系统的 MediaProjection 授权机制完全独立。

> 首次调用 `su` 时，Magisk 等会弹一次「授权」框需要用户确认，
> 因此探测超时给得比较宽松（20 秒），避免用户还没点就被判为"无 root"。

### 实现细节

- PNG 先写到应用私有缓存目录（`/data/data/<pkg>/cache`），
  App 自身必定可读、**不依赖存储权限**；失败再退回外部缓存目录。
- 解码后做「旋正 + 去透明通道」再交给 OCR 引擎
  （引擎对带 alpha 通道的画面表现不稳定）。
- 命令用 `sh -c` 包一层完整字符串传入，避免 `ProcessBuilder` 拆参数出错；
  同时排空子进程输出，防止缓冲区写满导致 `screencap` 阻塞。

## 五点五、摄像头实时识别（只认数字）+ 相册

「OCR设置」页里有一张 **摄像头实时识别** 卡片，点「打开摄像头识别」进入
一个全屏预览页：**调起后置摄像头，连续识别画面里的文字，但结果只保留数字**。

同一页还提供 **相册**：从文件选择器挑一张已有图片，用**完全相同的数字规则**
识别一次 —— 拍糊了、图是别人发来的、或者只是想事后补录，都不用重拍。

适用场景：抄小票金额、读电表水表读数、记车牌、录快递单号 ——
凡是「用眼睛抄一串数字」的活，都可以把手机对着它，等结果稳住后点一下复制。

### 界面与操作

| 元素 | 说明 |
|---|---|
| 顶部状态 | `识别中…` / `已暂停` / `相册识别完成…` / 出错原因（橙色） |
| 相册图片区 | 相册模式下显示原图，**含数字的行描绿框、框里写着这行抽到的数字**；双指放大、单指拖动、双击在 1x/2.5x 之间切换 |
| 中部大号数字 | 识别结果，**只显示数字**；点一下即复制 |
| 底部小字 | `共 N 个数字 · 耗时 xx ms · 识别到 M 行 · small`（末尾是**当前档位**；相册模式下前缀为 `相册图片`） |
| 相册 | 选一张已有图片识别一次，识别后显示原图并框出数字行（见下面「相册模式」） |
| 复制 | 把当前结果显示的数字复制到剪贴板 |
| 暂停 / 继续 | 停掉识别但**保留预览**；相册模式下标为「继续」，点它恢复实时 |
| 手电筒 | 暗光下补光；开关会重置一次预览请求，画面亮度立即跟随 |
| 节奏 | 快 `200ms` / 标准 `350ms` / 省电 `800ms` 三档循环 |

进入这一页会**自动申请相机权限**（第一次）。没有相机权限时页面只提示、
不崩。相册那条路**不依赖相机权限**，只是页面本身以相机为主。

### 用哪个引擎：跟随「OCR设置」里的档位

**这一页没有自己的引擎选择** —— 它用的就是你在「OCR设置」里选的那一档：

| 你的档位 | 这一页实际用的 |
|---|---|
| `tiny` | native PP-OCRv6（轻量模型） |
| `small` | native PP-OCRv6（高精度模型，**识别率最高**） |
| `rapid` | Google ML Kit（捆绑版） |

底部小字末尾会显示当前档位，换档之后能立刻看出「现在是谁在算」。
想换引擎就去「OCR设置」改，这一页不用单独设置。

> **前提：OCR 服务必须是启用状态。** 识别复用服务里那一份模型，
> 所以服务没开时这一页不能识别，状态栏会直接写明原因
> （`「启用 OCR 服务」已关闭` / `模型仍在加载中`），不会悄悄退回某个引擎。
>
> 为什么不另建一份：`libnjocr.so` 里的模型是**进程级单例**
> （`det_net` / `rec_net` / `is_loaded` 都是静态变量），整个进程只有一套。
> 另建既做不到，重复加载还会把服务正在用的模型顶掉。

### 相册模式

点「相册」→ 系统文件选择器 → 选中图片 → **原图立刻显示在页面上** →
识别完成后在**每一行含数字的位置描一个绿框、框里写上这行抽到的数字**，
同时下方照旧给出数字列表。

### 为什么要把图显示出来并画框

取件码、快递柜这类场景的输入常常是一张**很长的清单截图**：几十上百行，
每行一串四位数字。只把数字抽出来摆成一列，人是**对不上号**的 ——
究竟框的是哪一行、有没有漏、有没有把「货架号」也当成取件码，光看数字看不出来。
所以相册模式做两件事：

- **原图直接显示**：居中缩放，上方给返回栏、下方给结果面板让位
  （面板高度是 `wrap_content`，长了会顶上来，所以按实测高度动态留白）；
- **只给「这一行确实有数字」的行描框**：整张图每行都描框会糊成一片，
  反而看不出哪行是目标。框是亮绿色 + 极淡的绿色填充，黑白底上都够跳。
  填充只在**框没被撑高**时才画：长图上相邻行只隔几个像素，撑高的框一层层
  半透明绿叠上去会连成整片绿，所以那种情况下只留描边；
- **框里写数字**：光有框还得回头数「这是第几行」，所以把这一行抽到的数字
  直接写在框里（白色等宽字体 + 深色描边，黑底白底都读得清）。
  位置和形状只能一对一印证：框里写 `8512`，下方列表里就该有 `8512`；
- **能放大看**：长图整张塞进手机屏幕后单行只剩三五个像素高，框叠在一起
  根本看不清 —— 那这个框就等于没做。所以支持**双指放大（最高 8x）、
  单指拖动、双击在 1x/2.5x 之间切换**，平移到边缘会自动夹住。
  放大后框线按 `1/√scale` 变细，不会糊成一片粗边。

  框里的数字同理：**行高不到约 11 个屏幕像素就不画**——238 行的清单图
  1x 全屏时每行只有 6 像素，硬塞一串字只会得到一层白色噪点，
  叠在图上是负担而不是信息。放大到能读了它自己就出现，不需要开关。
  字号按「真实（撑高之前）行高 × 0.78」算，上限 13dp、放不下时横向压缩，
  并且 x 坐标夹在视口内 —— 否则放大后框左沿滑出屏幕，数字也跟着看不见了。

### 绿框为什么曾经一整个消失

换引擎之后（把这一页从固定 ML Kit 改成跟随「OCR设置」档位）绿框全没了，
原因不在画框代码，而在**两个引擎的 `type` 语义不一样**：

| `type` | native（PP-OCR） | ML Kit |
|---|---|---|
| `1` | 只有 `{"text":"0671"}` | 只有文本 |
| `2` | 只有**中心点** `{"x":2776,"y":3991}` | 中心点 + 宽高全套 |
| `3` | 左上角 + 宽高 `{"x":2729,"y":3953,"w":95,"h":77}` | 同上 |

原先统一用 `type=2`。ML Kit 在 `type>=2` 时就给全套 `x/y/w/h`，所以一直正常；
换成 native 之后每行只有中心点、没有 `w/h`，而解析代码要求**四项齐全**才建矩形，
缺一项就置空 —— 于是一个框都画不出来。

现在这一页统一用 `type=3`（两边都能拿到完整矩形），同时保留兜底：
某项只有 `x/y` 时按字符数估一个框，宁可不精确也不整片空着。

### 框高为什么要规整

native 给出的 `h` 是**文字检测框的外接矩形**，不是文字的实际高度。
对一张 3072×4096、约 238 行的取件码长图实测（`type=3`，466 个框）：

| 指标 | 实测值 |
|---|---|
| 框高 `h` 的 min / 中位 / max | `8 / 50 / 319` 像素（单字符 `"5"` 给了 `h=110`） |
| 真实行高（4096 ÷ 238） | 约 **17.2** 像素 |
| 跨行重叠的框对数 | **194** 对（原始） |

即 `h` 约为真实行高的 3~6 倍。照原样画，上下相邻的框大面积重叠，
淡绿填充（alpha 34）层层叠加，整片糊成一块绿 —— 那就等于没框。

所以画之前先**把框高压回行高量级**，做法是逐框局部约束而不是猜一个全局行距
（试过全局「同列相邻 top 差」的中位数，不成立：这份数据里大量 1~4px 的小间距
—— 同一个视觉行被切成多段 —— 把中位数拉到 9px，压完框高压到 1x 下只剩 5px，
框里的数字全被行高下限挡掉不画，等于为了修重叠把标签功能废了）：

1. 对每个框，只找**横向确实与它重叠**的框（重叠宽度 ≥ 两者较小宽的一半）；
2. 取这些框里「中心 y 距离」最小的值当 `gap` —— 那就是它最近的上下邻居；
3. 框高超过 `gap` 就压到 `gap`、保持纵向中心不变（压到 `gap` 时两框正好相切）；
4. 再做一次全局兜底：超过「框高中位数 × 3」的孤立大框也压掉。

只压不放 —— 小框保持原样。实测同一批数据：跨行重叠从 **194 对降到 10 对**，
框高中位 25px（1x 下约 8.8 屏幕像素），最大框高压到 75px，不再有整片绿。

### 长截图为什么不会被压糊

原来的做法是「最长边上限」等比缩放。对一张 `1080×8000` 的清单截图来说，
缩到最长边 1920 之后**宽度只剩 345 像素**，一行四位数字连笔画都挤没了，
识别率断崖下跌。所以改成两条规则同时约束：

| 约束 | 值 | 为什么 |
|---|---|---|
| 宽度上限 | `2400` 像素 | 太宽对识别没帮助，只烧内存 |
| 总像素上限 | `1200 万`（约 48MB ARGB_8888） | 防 OOM |
| 分块高度 | `1400` 像素 | 见下 |

宽度**不被牺牲**。而高度超长这件事交给**分块识别**解决：ML Kit 拿到一张
8000 像素高的图会自己缩到很小的尺寸再认，小字直接消失；切成 1400 高的块
逐块送进去，每块的字高才是原始字高。

分块的两个细节：

- **相邻块重叠 160 像素**：不重叠的话，正好压在切缝上的那一行会被切成两半，
  两边都认不出；
- **按「行中心」归属，不重复不遗漏**：每块只采纳行中心落在本块专属区的行。
  不用「框完全在本块内」是因为压在切缝上的行框必然跨块，那样会两边都不收。
  块内判到的 `y` 会加回整图坐标，所以框仍然画在正确位置
  （否则第二块以后所有框都会偏移一个块高）。

识别时顶部状态会显示 `长图分块识别中… 3/7`，几秒的空档不至于让人以为卡死。

几处刻意设计：

- **用 `ACTION_OPEN_DOCUMENT`，不读相册数据库**：走 SAF，
  **不需要 `READ_EXTERNAL_STORAGE` / `READ_MEDIA_IMAGES`**
  （Android 13 换过一次权限名，适配成本高、用户也嫌烦）；而且能选到
  「下载」「网盘」「聊天记录」里的图，不限于相册 App。
- **先量尺寸再解码**：相册图动辄 4000×3000，直接 ARGB 解码要 48MB，
  低端机容易 OOM。`inSampleSize` 按「宽度 ≤ 2400 且总像素 ≤ 1200 万」
  算后再解码（**不按最长边**，原因见上一节）。
- **按 EXIF 转正**：竖着拍的照片像素其实是横着存的，只有 EXIF 记了
  「转 90 度」。不转正就送识别，等于把整张图躺倒着认，识别率会明显下降。
  8 种 EXIF 方向（旋转 3 种 + 镜像 2 种 + 转置 2 种）都处理了。
- **识别完把界面「钉住」并暂停实时**：不钉住的话，摄像头下一帧就把
  你刚看清的结果盖掉了。要回到实时识别，点「继续」（同一个按钮兼作
  「解除钉住」）。
- **取消选图不改你的状态**：原来什么状态（跑着还是暂停着），取消后就是
  什么状态，不会擅自把你拽回实时。
- **「空」有两种，文案分开说**：`（这张图里有文字，但没有数字）` vs
  `（这张图里没识别到文字）` —— 免得把「确实没数字」误读成「识别失败」。

### 数字是怎么抽出来的

识别引擎给的是整段文字，本页只从中抽数字，规则如下：

1. **全角转半角**：`０-９` → `0-9`、`．` → `.`（中文单据上全角数字很常见）；
2. **千分位逗号去掉**：`1,234` → `1234`、`1,234.56` → `1234.56`；
3. **剩下的逗号当小数点**：`1,23` → `1.23`（欧洲写法）；
4. 按 `\d+(\.\d+)?` 抽，**负号不保留** —— 单据上的 `-` 绝大多数是分隔符，
   保留它会把 `2024-001` 拆成 `2024` 和 `-001`，反而更难用；
5. **只在同一行内去重**：同一行紧挨着的重复值只留一个，
   但「单价 12.00 / 小计 12.00」这种分处两行的相同数字**两条都留**。

⚠️ 已知取舍：像 `货架号 2-2` 这种**货位编号**也会被抽出来（结果是 `2`），
因为规则只看「是不是数字」，看不懂中文语义。从绿框能一眼看出哪几行被认了，
嫌碍事的话可以手动挑。

几个实测过的例子：

| 识别到的原文 | 抽出的结果 |
|---|---|
| `合计：1,234.56 元` | `1234.56` |
| `金额 1,000,000 元` | `1000000` |
| `单价 12.00` + 换行 + `小计 12.00` | `12.00` / `12.00`（两行都留） |
| `订单号 2024-001 号` | `2024 001` |
| `编号：１２３４５` | `12345` |

### 为什么结果不是每一帧都刷新

手持时机身会抖，同一行数字偶尔会掉一两位，如果来一帧刷一次，结果区会疯狂
闪烁、还容易抄错。所以这里要求**连续 2 次抽出的结果完全一致**才更新界面：
抖动被吃掉，真数字一稳住就立刻显示。

### 实现要点

- **用系统 Camera2，不引 CameraX**：CameraX 要再加四个 androidx 库
  （`camera-core` / `camera-camera2` / `camera-lifecycle` / `camera-view`），
  而 `android.hardware.camera2` 是平台 API，**零新增依赖**，APK 不会变大。
- **识别器自己建，不借服务**：`OCRService` 不接受 `bindService`（`onBind`
  返回 `null`）也没有单例，而 `MlKitEngine` 是包内可见类，本页直接 `new`
  一个即可。模型是 bundled 版（不联网、不依赖 Play 服务），退出这一页时
  `close()`。
- **帧尺寸短边封顶 720**：识别耗时大致随像素数线性增长，1280×720 足够读清
  小票上的数字；再往上只是让每一帧慢一倍，对准确率几乎没帮助。
- **预览走重复请求、识别走单帧请求**：预览是连续的（AE/AF 一直在收敛、
  画面流畅），识别则另外用一次 `capture()` 插一帧给 `ImageReader`。
  这样识别频率由节奏档位决定，而不是被帧率拖着跑满 CPU。
- **YUV → NV21 → JPEG → Bitmap**：按 `rowStride` 逐行取值，不依赖
  buffer 的 position/limit —— 部分机型 UV plane 带 padding，按宽直接取
  会把画面搓成斜的。
- **有抓帧看门狗**：10 秒内没等到图像就强制解锁重试，避免整条链路卡死。

### ⚠ 耗电与发热

实时识别是**持续占用相机 + 持续推理**，功耗明显高于「截一次再识别」：

- 连续跑几分钟，机身会明显发热，部分机型会开始降频；
- 页面开着时屏幕常亮（`FLAG_KEEP_SCREEN_ON`），也会额外耗电。

所以设计成**用完就退**：离开这一页（`onPause`）立刻关相机、停识别，
识别器也在 `onDestroy` 里释放。不要把它当监控挂着。

## 六、边缘滑动手势

在屏幕边缘放一个可拖动的**手柄**，手指从手柄上划过设定距离即触发
（滑过即响应，不必抬手）。共 **8 个方向**（上/下/左/右 + 四个斜向），
每个方向的触发距离可单独调，也可让某个方向不响应。

设置入口：App 主界面 → **滑动触发** 页。

### 与宏的配合

手势引擎本身**不执行任何动作** —— 它只做一件事：告诉 MacroDroid
「某个方向的手势成立了」。真正干什么由宏决定。

配置步骤：

1. 「滑动触发」页 → **打开手势设置**，添加手柄（位置、宽度、颜色、可触发方向）
2. 在 MacroDroid 里新建宏 → 触发器 → **小孙OCR · 边缘滑动事件**
3. 在插件配置界面选定**方向**（不匹配时插件直接回 17，宏不会跑）
   —— 选完会**排他地**同步到手柄：只留选中的那个方向，其余自动关掉，
     **不用再回手柄编辑页勾一遍**
4. 展开 **Output variables**，把菜单三项映射到宏变量

### 滑动菜单（跟手滑出）
开启后，滑过触发距离**不再立即触发宏**，而是弹出一排按钮；
继续滑到某一项上（跟手高亮），抬手才选中它。

**没选中就不触发宏**：抬手时手指不在任何按钮上（滑到空白处松手），
或者这批触摸被系统抢走 —— 这两种情况**连通知都不发**，
MacroDroid / Tasker 侧完全没反应（不会出现「触发了但变量是空的」）。
只有真的压在某个按钮上抬手，才会把结果送过去。

配置页：**滑动触发** 页 → **滑动菜单**。
（改完返回，「滑动触发」页那张卡片的副标题会立刻跟着变 —— 开关状态和项数都是回来时重读的。）

可调项：

| 分组 | 项目 |
|---|---|
| 开关 | 启用 / 关闭 |
| 外观 | 图标大小、显示文字、文字大小、文字间距、浅色圆底 |
| 布局 | 每排数量、逐排数量（逐排单独覆盖）、图标间距、每排间距 |
| 配色 | 圆底颜色、文字颜色、选中颜色（支持 `#RGB` / `#ARGB` / `#RRGGBB` / `#AARRGGBB`） |
| 交互 | 热区大小（命中半径 = 图标半径 × 倍率，100%~300%，带感应范围预览） |
| 菜单项 | 添加 / 改名 / 选图标 / 排序 / 删除 |

菜单项有三个字段：

| 字段 | 说明 |
|---|---|
| 名字 | 按钮上显示的文字，必填 |
| 动作值 | 回传给宏的 `%xsocr_menu_action`；留空则与名字相同 |
| 图标 | `app:包名` / `file:路径` / 资源名，留空则显示名字前两个字 |

> **动作值为什么要单独一栏**：名字是给人看的、动作值是给宏比的。
> 按钮可以叫「微信」而动作值叫 `wechat`，宏里的判断比按序号好读得多。

**排列方式**：图标沿 45° 斜线从左下排到右上，**每排各自居中**；
一排排满就在上方另起一排（每排数量可逐排单独设置）。
从触发位置弹出，出屏时先平移圆心再整体等比缩小。

> **菜单项没填图标时**：用名字的**前两个字**顶着（名字本来就只有一个字，就显示一个字），
> 字号会自动收窄一点。只取一个字（早先的行为）认不出来 ——
> 「微」「设」这种完全看不出是哪个应用。设置页的缩略图预览与实际绘制**共用同一套规则**。

### 为什么菜单必须由本应用弹

普通做法走不通，卡在 Android 输入分发的一条硬规则上：

> `InputDispatcher` 在手指按下（`ACTION_DOWN`）那一刻做一次命中判定，
> 把**整条触摸序列**绑定给当时那个窗口。此后 MOVE / UP 只投递给它。
> 中途新建的窗口收不到 MOVE（无法跟手高亮），也收不到 UP（无法判定选中）。

官方**没有任何 API** 能把进行中的触摸序列转交给别的窗口或进程。
更关键的是：宏的 Java 动作是**一次性脚本**，跑完即退，根本没法常驻持有窗口。
所以菜单由**已经拿住那次触摸的那个悬浮窗**自己弹（`EdgeGestureService`）。

关键在于**宏被唤起的时刻，正是手指抬起的时刻** —— 所以宏侧既不需要常驻，
也不需要处理「手指还按着」的中间态，只是在「发生了」之后按结果做事。

### 屏蔽系统侧滑返回

手势导航下，系统是从屏幕边缘往内判定「返回」的，优先级比应用窗口还高 ——
手柄贴着边缘时，手指刚碰上去就被系统当成返回吃掉了，表现为「条子在那儿但按不动」。

本应用用平台 API `setSystemGestureExclusionRects()`（API 29+）申请排除区，
**非 MIUI 专属**。开启的手柄会实时上报自己的矩形，系统据此把这一小条的
边缘手势让给应用。

> ⚠️ **Android 10 以下没有这个能力。**
> `setSystemGestureExclusionRects()` 是 **API 29（Android 10）** 才加入的
> 平台接口。在 Android 9 及更早的机型上，**没有任何原生手段**能让应用
> 从系统手里抢回边缘手势 —— 不是配置问题，怎么调都不会生效。
> 换手机测试时最容易踩这个坑（开发机是 Android 17 一切正常，
> 旧机器上就「屏蔽失效」）。
> 编辑页在 `SDK_INT < 29` 时会**直接显示一条橙色警告**说明此事；
> 服务侧的日志里也会记一条 `系统手势屏蔽不可用: sdk=xx < 29`。
> 临时办法：把手柄挪到屏幕偏中间的位置（避开系统边缘返回区），或改用三键导航。

> 另外，**每个手柄自己有一个「屏蔽本条手柄区域的系统手势」开关**
> （默认开）。关掉的手柄不上报排除区 —— 排查「屏蔽没生效」时先确认
> 这个开关是不是被关掉了，日志里会记 `该手柄未开启屏蔽系统手势: <名字>`。

> 曾经还提供一个「整个边缘」选项（把整条边都变成触摸区），**已移除**：
> 整条边全变触摸区会让系统侧滑返回彻底失效、触摸目标混乱。
> 现在只保留「手柄条 + 调宽」这一条路 —— 手柄宽度可调范围 `[0, 200] dp`。

### 防烧屏（像素漂移）

手柄是**常驻悬浮窗**（默认 `8 × 150 dp`，贴着边缘、位置常年不变），
OLED 屏会顺着它的形状慢慢留下残影。

开启后（默认开，设置页可关）手柄每隔一段时间在**垂直方向**随机挪动几个像素：

| 项 | 默认 | 范围 | 说明 |
|---|---|---|---|
| 防止烧屏漂移 | 开 | — | 总开关 |
| 漂移幅度 | `8 dp` | `0 ~ 30` | `0` = 原地不动 |
| 漂移间隔 | `60 秒` | `15 ~ 300` | 每隔多久换一次位置 |

几个刻意的取舍：

- **只上下挪、不左右挪。** 手柄的语义是「贴着屏幕边缘」，
  横向一移看起来就像位置错了；竖直方向的漂移不破坏这个语义，
  而防烧屏效果一样有（竖条的上下边界照样错开了）。
- **漂移是临时的。** 偏移只改窗口的 `y`，**不写回 `offsetPercent`** ——
  用户拖到哪、它就还属于哪。重启服务或关掉开关会拨回原位。
- **不干扰操作。** 菜单展开时窗口是全屏的、拖拽中、以及手指正按在
  手柄上时都不漂移。（顺带一提：手势方向判定用的是 `getRawX()/getRawY()`
  屏幕绝对坐标，本来就不受窗口平移影响。）
- **息屏不做。** 屏幕不亮时手柄也不显示，省掉无谓的窗口事务。

> 为什么用「漂移」而不是降低不透明度：手柄存在的意义就是**看得见、摸得着**，
> 调暗会损害可用性；漂移只挪几个像素，肉眼几乎察觉不到，两者代价不对等。

## 八、使用步骤

1. 安装 APK，首次启动会申请「所有文件访问权限」。
2. **打开 App 即自动启动 OCR 服务**（无需手动点启动）。
3. 首次启动需在后台加载模型（约 1~3 秒），界面上方会显示服务状态。
   > **冷启动行为（修复⑥）**：服务采用「HTTP 先上线、模型后台加载」，
   > 因此**端口会立刻可连**（`GET /last` 秒回），但此时识别尚未可用：
   > `POST /` 会返回 `503 {"status":503,...}`，`/last` 里的 `modelReady` 为 `false`。
   > 插件会自动轮询等待模型就绪后再发识别请求，无需人工干预；
   > 自己写脚本调用时，请以 `modelReady` 或 `503` 作为"稍后重试"的信号。
4. 切到「**OCR设置**」页，输入图片路径或选择图片，选择格式，点击 **开始识别**。
5. 也可由自动化脚本直接调用 `127.0.0.1:1666`。
6. 想用边缘滑动手势，切到「**滑动触发**」页启用，并在 MacroDroid 里
   加触发器「小孙OCR · 边缘滑动事件」。

> 界面只有「**OCR设置** / **滑动触发**」两个页签；服务随 App 启动自动运行。
> 「OCR设置」页顶部那张开关卡控制 OCR 服务本身（关掉后接口不再监听、也不开机自启），
> 它与边缘滑动手势**互不影响** —— 只用手势触发宏的人可以把 OCR 服务关掉。
> 注意：从最近任务划掉 App 时，本服务**不会**随之停止 —— 服务在 Manifest 中声明了
> `android:stopWithTask="false"`，正是为了让外部自动化脚本的调用不因清理后台而中断。
> 如需彻底停止，请在系统设置中「强行停止」应用，或调用系统停止服务接口。

## 九、从最近任务隐藏

「OCR设置」页有一张开关卡：**从最近任务隐藏**（默认关）。

开启后，多任务界面里不再出现本应用的卡片，但**服务照跑、手势照用**，
从桌面图标照常进入。

### 为什么不用 Intent 标志

这是踩过一圈坑的地方，记下来免得重走：

| 方案 | 结果 |
|---|---|
| `Intent.FLAG_ACTIVITY_EXCLUDE_FROM_RECENTS` | ❌ 只在 task **首次创建**时记进 `baseIntent`，之后补的标志会被丢掉 |
| `TaskDescription` 里的 `excludeFromRecents` | ❌ 该类**根本没有**这个字段（`ActivityManager$TaskDescription` 无此 API） |
| 带标志**重建** task | ❌ 系统会**复用已存在的 task**（task id 不变），后到的标志同样被丢 |
| **`ActivityManager.AppTask.setExcludeFromRecents()`** | ✅ 就地改、立即生效、无需重建 |

正确做法是拿到本应用的 task 列表逐个设（API 21+）：

```java
ActivityManager am =
        (ActivityManager) ctx.getSystemService(Context.ACTIVITY_SERVICE);
for (ActivityManager.AppTask t : am.getAppTasks()) {
    t.setExcludeFromRecents(hidden);   // hidden = 是否隐藏
}
```

设置值存在 `xsocr_prefs` 的 `hide_from_recents`（默认 `false`，老用户行为不变）；
`MainActivity` 在 `onCreate` / `onResume` 各对齐一次，拨开关时**当场生效**
（不用切出去再进来）。

> 与第八节末尾那条「划掉 App 服务也不停」**不冲突**：那条说的是
> `android:stopWithTask="false"`，管的是**服务存活**；
> 这个开关管的是**卡片显不显示**。两件事，可以同时要。

## 十、日志与排障

有些问题**只在别人的手机上出现**（「点滑动菜单闪退」「系统手势没屏蔽」），
开发机上怎么试都正常。这时唯一的路是拿到对方设备上的现场记录 ——
但要求普通用户开 USB 调试、装 adb 抓 logcat 是不现实的。

所以本应用自带一套日志：**崩溃自动记，用户只负责点一次「分享日志」**。

### 怎么用（给测试用户的话）

1. 复现一次问题（崩溃不需要刻意复现 —— 发生时就自动记下了）
2. 打开 App →「滑动触发」或「OCR设置」页 → 最下面的**日志**卡片
3. 点 **分享日志** → 选微信/QQ/邮件发出去
   （发不出去就点 **导出到下载**，文件会落在 `Download/小孙OCR日志_日期时间.txt`）
4. 想先自己看一眼：点 **查看日志**，弹窗里长按可以只复制关键几行

「分享日志」会**自动带上设备信息**（机型 / 系统版本 / ROM / 屏幕参数），
这些是排障第一问，不用用户自己找。

### 日志落在哪

```
Android/data/com.xiaosun.ocr/files/logs/xsocr_log.txt
```

放在**应用自己的外部私有目录**：不需要任何存储权限、卸载时自动清理、
通过 FileProvider 能合法分享给微信/QQ/邮件。

> Android 11+ 的系统文件管理器不让进 `Android/data`，所以**不要**指望
> 用户自己去翻文件 —— 界面上给了「分享」和「导出到下载」两条路。

### 记了什么

| 类别 | 内容 |
|---|---|
| **崩溃（自动）** | 完整堆栈 + 线程名，`Thread.setDefaultUncaughtExceptionHandler` 抢在系统前面落盘 |
| 会话开始 | 设备信息、SDK 版本 |
| 手柄 | 每个手柄的窗口宽高、y 坐标、贴边、类型、是否屏蔽系统手势、屏幕尺寸 |
| 菜单 | 展开请求（项数/图标数/布局/命中倍率/锚点）、布局结果、首帧、选中项、取消 |
| 手势排除 | 每次上报的矩形与结果；**低版本无法屏蔽**、**手柄没开屏蔽**都会明确记一条 |
| 设置页/服务 | onCreate、手柄重建数量与总开关状态 |

### 两个刻意的设计

- **不影响主流程。** 所有写文件操作都在单线程池里，任何 IO 异常都被吞掉 ——
  日志记不上是小事，把功能搞崩是大事。唯一例外是崩溃处理：那时进程马上要死，
  必须**同步**写完再交给系统。
- **文件不会无限长大。** 超过 512KB 就轮转成 `xsocr_log.old.txt`
  （上一份被覆盖），最多占两份空间，用户随时发过来都是最近的一段。

### 顺带修的三个「不该崩」的地方

排查崩溃时发现的薄弱点，一并加了兜底（**崩了只是功能不灵，不该整个应用退出**）：

| 位置 | 原来的问题 | 现在 |
|---|---|---|
| `GestureView.onDraw` | `onDraw` 抛异常会一路冒到 `ViewRootImpl`，**直接崩掉进程** —— 第三方图标 Drawable、异常尺寸、字体度量都可能抛 | 整段绘制套兜底，画不出来只跳过本帧 |
| `drawMenu` 图标绘制 | 某个应用的图标 `setBounds/draw` 抛异常会带崩整个菜单 | 单个图标失败就退化成文字（和「没配图标」的显示一致） |
| `tryOpenMenu` / `hitMenu` | 配置解析、加载图标、窗口改全屏，任一环出意外就闪退 | 整体兜底 + 恢复窗口尺寸，用户看到「这次没弹出来」而不是「应用不见了」 |

配合崩溃自动记录，下次拿到日志就能直接定位到具体哪一行、哪个图标。

### 一次真实的崩溃复盘

日志功能加好当天，测试机就传来第一份现场：

```
20:57:06.397 E/CRASH 未捕获异常，线程=main
java.lang.IndexOutOfBoundsException: Index 0 out of bounds for length 0
    at com.xiaosun.ocr.EdgeGestureMenuActivity$HitPreview.onDraw(EdgeGestureMenuActivity.java:1160)
    at android.view.View.draw(View.java:...)
    ... ViewRootImpl / Choreographer
```

**一句话结论：菜单项为空时，进「滑动菜单」配置页必崩。** 与机型无关。

原因在 `HitPreview.onDraw`（配置页顶部那张「感应范围预览图」）：

```java
int n = Math.max(1, items.size());   // ← 空菜单时 n 被强行抬成 1
...
String txt = items.get(i).text;      // ← items 长度 0 → 越界
```

那句 `Math.max(1, ...)` 的本意大概是「空菜单时也别留白」，但它让
**循环次数**和**列表长度**对不上了。而「菜单项为空」是最正常的初始状态
（新装用户、或刚把最后一项删掉），这一页一进来就要画预览 —— 于是必崩。
开发机上菜单早就配好了，所以一直复现不出来。

> 这也说明上一节那三处兜底**没兜住这个**：崩的是配置页的预览视图
> `HitPreview`，不是悬浮窗的 `GestureView`，两者是各自独立的 `onDraw`。

修复：

- `n` 改用真实的 `items.size()`，为 0 时画一句「菜单还是空的，先在下面「菜单项」里添加」就返回；
- `onDraw` 整体再套一层兜底（`onDrawInner`），万一还有别的意外，也只是这一帧画不出来，记一条日志继续跑；
- 顺手给 `buildItemCell` / `showItemMenu` 的 `items.get(index)` 加了边界检查 —— 真错位了只该少画一格，不该闪退。

教训记在这里：**凡是「循环次数」和「数据长度」被分开维护的地方，
都要按最坏情况（长度为 0）想一遍。**
